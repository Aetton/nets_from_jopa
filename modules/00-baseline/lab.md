# Baseline lab

Теория умеет очень убедительно притворяться знанием. Поэтому теперь руками.

Нужен Linux-хост с root и пакетами `iproute2`, `tcpdump`, `iputils`, `curl`, `dig` или `drill`, `ss`.

## Lab 1. Найди путь пакета

Выбери любой доступный IP вне своей локальной подсети.

Сначала, **до запуска команд**, запиши предположение:

- какой source IP будет выбран;
- через какой interface уйдёт пакет;
- какой next hop будет использован;
- чей MAC понадобится системе.

Затем проверь:

```bash
ip route get <IP>
ip neigh
```

После этого сними трафик:

```bash
sudo tcpdump -eni <iface> 'arp or icmp'
```

Очисти подходящую neighbour-запись или выбери адрес, к которому давно не обращался, и посмотри последовательность событий.

**Зачёт:** можешь до capture предсказать, какой MAC будет destination у Ethernet frame: конечного хоста или gateway.

## Lab 2. Namespace без Docker

Создай два namespace и соедини их veth-парой.

Цель:

```text
ns-a  <------ veth ------>  ns-b
10.200.0.1/24             10.200.0.2/24
```

Добейся ping между ними.

Минимальный набор инструментов:

```bash
ip netns
ip link
ip addr
ip route
```

После запуска объясни:

- где физически существует каждая половина veth;
- где находятся IP-адреса;
- что увидит `ip link` снаружи namespace;
- что увидит `ip link` внутри него.

**Бонус:** сними ICMP одновременно с обеих сторон veth.

## Lab 3. Убей маршрут

В namespace-топологии создай третий namespace, который будет маршрутизатором между двумя разными подсетями.

```text
client ---- router ---- server
```

Затем последовательно ломай:

1. route на client;
2. `net.ipv4.ip_forward` на router;
3. обратный route на server.

Каждый раз фиксируй:

- где пакет перестал появляться;
- что показывает `ip route get`;
- чем симптомы отличаются между тремя поломками.

## Lab 4. TCP глазами tcpdump

Подними любой TCP listener, например:

```bash
python3 -m http.server 8080
```

С другой машины или namespace подключись к нему и запиши capture:

```bash
sudo tcpdump -nn -i any tcp port 8080
```

Найди:

- SYN;
- SYN-ACK;
- ACK;
- передачу данных;
- закрытие соединения.

После этого ответь: какие пакеты ты ожидаешь увидеть при `connection refused`, а какие при простом timeout?

## Lab 5. DNS не равен DNS

Сравни результаты:

```bash
getent hosts example.org
dig example.org
```

Посмотри:

```bash
cat /etc/nsswitch.conf
cat /etc/resolv.conf
```

Если система использует `systemd-resolved`, дополнительно:

```bash
resolvectl status
resolvectl query example.org
```

**Зачёт:** можешь объяснить, почему `dig` не является полным эквивалентом того DNS-resolution, который делает обычное приложение.

## Lab 6. Собери диагностический снимок

Представь, что тебе дали Linux-машину со словами «сеть не работает».

За пять минут собери минимальный набор данных, достаточный для первого диагноза.

Не используй готовый скрипт. Запиши команды в том порядке, в котором реально стал бы их выполнять.

После этого объясни, почему каждая команда стоит именно там.

> Если первым пунктом оказался `ping 8.8.8.8`, ничего страшного. Курс как раз существует потому, что человечество заслуживает второй шанс.
